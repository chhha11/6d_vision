# 深度采集卡死与异常退出修复

原故障记录：`data/tracking/live_depth_6dof/20261101_124734/`。第 21 次采集被工作进程的 60 秒超时中止，第 22、23 次又成功初始化。第 2 次深度进程以 `0xC0000005`（访问冲突）退出，第 7、10 次以 `0xC0000374`（堆损坏）退出。这些属于 OpenNI 原生采集进程故障。

最后一次跟踪器写出了完整的总结并请求重采深度；之后没有新一轮记录。原版本在这个位置直接重开 RGB，失败会使主程序退出。由于当时没有保存 traceback，最后窗口退出的确切原因不能确认，也不能把此前的子进程崩溃直接当作主进程崩溃。

## 本次处理

- 深度采集保持独立进程。直播默认总超时从 60 秒改为 **8 秒**，单帧先使用 OpenNI 的 **2 秒有限等待**；驱动即使忽略有限等待，父进程仍会杀掉并回收工作进程。进程退出确认前不会重开 RGB。
- 采集期间 Q、Esc 和关闭窗口会发出取消信号。深度进程会被回收；普通后台任务须结束后才能安全释放其相机资源。
- 五帧都复制到 NumPy 自有内存后立即关闭深度流、设备和 OpenNI，再计算中值、压缩和保存文件，缩短 USB 原生线程存活时间。五帧中值、标定、位姿质量和运动检查保留，拟合仍与 RGB 恢复并行。
- 初次开机、深度结束和跟踪器请求重采后的 RGB 重开失败都会在同一个窗口重试。处理搜索/预览/跟踪阶段暂时读不到 RGB 帧的情况，释放失效相机后恢复并重新定位。
- 失败不会复用上一轮位姿或半写入的深度文件。深度失败后恢复 RGB，返回搜索/重试；新位姿通过检查后才显示 6DoF 框。
- 每次原生阶段前保存 `depth/capture_progress.json` 和 `capture_events.jsonl`；`depth/worker.log` 保存输出、原生异常栈和看门狗超时。会话目录保存 `session_events.jsonl`、未恢复异常的 `last_error.txt` 和原生主进程错误的 `native_fault.log`。

仍运行：

```powershell
python -m core.live_depth_6dof
```

可使用 `--depth-timeout-s` 和 `--depth-frame-timeout-s` 调整时间。8 秒限制仅作用于深度子进程，不是完整初始化耗时，也不覆盖 DirectShow 原生调用永久不返回的情况。当前 RGB 重开使用有限次数的一组调用，失败后在界面重试；不能用 Python 线程取消强行终止已经进入 DirectShow 的原生调用。

## 实机证据与边界

`data/tracking/evaluations/depth_recovery_20261101/report.json`：三次 RGB→深度→RGB 循环，第二次复现 `0xC0000374`，父程序继续，约 1.24 秒恢复 RGB，第三次深度成功。异常栈在五帧复制后的 `numpy.savez_compressed` 导入阶段发现堆损坏，不能据此认定该函数是破坏内存的源头。

关闭深度流提前后的检查见 `data/tracking/evaluations/depth_recovery_20261101_fixed/report.json`。两次实际深度采集成功（约 1.08–1.11 秒）；中间一次 RGB 首次重开两次均失败，随后恢复。这也验证了 DirectShow 临时不可用的情况。小样本成功不能证明旧版驱动的堆损坏已根治；本次主要建立故障隔离、快速回收和恢复机制。

最后一组见 `data/tracking/evaluations/depth_recovery_20261101_final/report.json`：连续五次深度采集与 RGB 恢复全部成功，深度子进程 1.06–1.15 秒，RGB 恢复 1.23–1.24 秒。五组输出均验证为五帧 640×480 uint16 深度与相同大小中值图。这组测试没有运行 YOLO 和 6DoF 拟合，因此上述数值不是完整目标重定位耗时。

自动回归覆盖真实睡眠子进程的超时回收、取消回收、非零退出日志、Q 取消、RGB 重开失败重试、深度失败后下一轮跟踪、重定位后 RGB 重开失败、异常 traceback 保存、OpenNI 单帧超时、驱动先关闭再保存及深度数组所有权。完整跟踪长时间运行仍需用户实际运动场景复测。

完整测试通过 139 项；最后调整工作进程回收与 RGB 重试相机索引后，相关 21 项测试再次通过。原文件副本保存在 `data/tmp/before_depth_hang_fix/`。
