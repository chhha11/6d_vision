# 相机身份固定与姿态切换卡顿处理

## 故障依据

用户会话 `data/tracking/live_depth_6dof/20261101_133529/` 有四次深度初始化。第 1、4 段跟踪约 4.6–4.9 秒后因连续框冲突请求重定位；另两次初始化分别因没有匹配深度簇、采集期间 RGB 场景发生变化被拒绝。普通跟踪运算约 1.5 ms，重新选点约 7 ms，读 RGB 帧约 44 ms。明显停顿主要发生在 RGB/深度切换及失败重试阶段。

旧版本只在启动时解析相机名称，此后一直使用同一个 DirectShow 数字索引。相机释放、重开期间若 Windows 重排设备，原索引可能指向电脑摄像头。现场已枚举到 `USB Camera`（Astra）和 `Integrated Camera` 两台设备。原日志没有记录物理设备路径，不能据此证明用户那次误切换的确切过程。

## 改动

- `core/camera_identity.py` 固定启动时选择的相机 `DevicePath`。初次打开和每次恢复均重新查询该物理设备的当前索引，打开后再次核对；路径消失或顺序在打开期间变化时释放并重试。恢复过程不会改用其他摄像头。OpenCV 的 DirectShow 接口仍按数字索引打开，这里的措施是在打开前后验证身份，并非直接按 moniker 建立采集图。
- 会话日志记录 `rgb_identity_pinned` 事件，跟踪总结记录相机名称和物理路径。USB 设备失联时保持原窗口重试，Q 或 Esc 退出。
- 跟踪器请求重定位时将仍然打开的 RGB 交还搜索阶段，直到真正采深度才释放。正常退出或读帧失败仍释放相机，避免多余的一次关闭、重开和预热。
- 搜索阶段仅保留一个后台 YOLO 任务，前台继续读取和显示 RGB，不堆积旧帧。超过 0.5 秒的检测结果清空确认状态；确认完成后不再启动一次无用推理。
- 深度备用入口继续显示 2D 检测框，确认同一个目标，并等待约 0.35 秒画面稳定后才采深度。检查包括框的位置/大小，以及框内图像变化；即使框不变，目标仍在转动也会重置等待。累计运动检查可捕捉缓慢变化，均匀亮度偏移会被扣除。RGB 当前帧初始化通过时直接交接，不受这段等待限制。
- 现在默认启用 RGB 优先入口：成功的 RGB-D 初始化会把可见 CAD 表面特征和米制 3D 点缓存起来。目标在运动中再次进入画面时，YOLO 框先限定搜索区域，AKAZE 匹配和 PnP 在当前 RGB 帧直接求出当前 6DoF；再用光流把匹配点跟到最新一帧后才交给 CAD 跟踪器。因此不必等待目标静止，也不会把深度采集前的旧位姿直接套到新画面。没有可用参考视图或匹配不足时，系统自动退回原来的深度初始化路径。

五帧深度中值、640×480 标定、位姿质量检查、采集前后运动检查和深度独立进程看门狗继续使用。图像稳定检查是降低失败重采的启发式判断，不能代替深度质量验证，也不能保证所有无纹理物体的运动都能被发现。

## 验证证据

实机短测 `data/tracking/evaluations/camera_identity_motion_20261101/` 完成一次初始化和 30 帧跟踪，无重定位或原生崩溃。

实机交接检查 `data/tracking/evaluations/camera_identity_motion_20261101_handoff/` 通过模拟 D 键请求一次新深度，验证首次跟踪退出后 RGB 仍打开。两轮初始化仅重开 RGB 两次，省掉交接阶段原来多余的一次约 1.2 秒重开。两轮完整初始化为 3.02、2.70 秒；深度采集为 1.15、1.07 秒，RGB 恢复约 1.22 秒，拟合与恢复并行。这不是对所有姿态和光照条件的耗时保证。

运动首帧回放 `data/tracking/evaluations/rgb_moving_initialization_20261101/`：前 24 帧为空，目标随后在连续合成平移/旋转中出现；程序读取 179 帧，深度切换次数为 0，6DoF 跟踪 40 帧全部有效。该回放的源图像外观在参考库中；不会要求应用时目标再次停住。

参考库加载后来改为与 CAD 几何准备并行，前台持续搜索。最后一次 `live_handoff_parallel/` 回放读取 90 帧，深度调用为 0，后续 40 帧中 33 帧为 TRACKING、7 帧为 VERIFYING POSE，最终有效，无重定位。参考准备约 1.66 秒，几何准备约 1.90 秒；这次回放预先准备了检测器，以上不是程序冷启动总时间。该改动后相关 30 项测试再次通过。

真实 RGB 短测 `real_rgb_short/` 也从 `rgb_reference_pnp` 入口进入，运行 45 帧后正常退出，没有打开深度流。状态计数为 TRACKING 36、TRACKING HOLD 1、VERIFYING POSE 6、RGB RECOVERED 1、SEEDED 1，最终位姿有效。未安排人为移动相机，因此只能验证真实 RGB 流和新入口交接，不能算移动相机验收。

使用未参与参考库的六张实机图像，各做五组仿射运动变换，共 30 个独立样本，YOLO 检出 19 个，最终 PnP 通过 3 个。其余视角仍缺少可靠特征支持；收紧多参考检查后，没有保留此前约 20 px 中心偏差的弱匹配。通过样本约 129–166 ms（包含 YOLO），中心误差约 1.1–3.1 px，长轴误差约 0.5–0.6°。该结果验证了运动初始化路径和延迟量级，也表明当前参考覆盖不足；不能宣称任意视角已解决。图像仿射变换不等同于真实手持相机引起的三维透视、遮挡和运动模糊。

自动回归覆盖设备重排、设备消失、打开过程中重排、原相机恢复、重定位相机所有权、检测期间持续读帧、过期检测失效、确认后无多余推理、RGB 当前帧 PnP、运动后光流交接，以及框不变而目标转动时延后采深度。上述实机短测没有人为持续转动物体，也没有物理拔插验证；运动判断和重排行为由自动测试验证。

最终 `python -m unittest discover -s tests -p "test_*.py" -q` 通过 **158 项测试**（48.12 秒）；`python -m compileall -q core tests` 通过。

## 使用与边界

```powershell
python -m core.live_depth_6dof --camera-name "USB Camera"
```

RGB 优先为默认设置，可用 `--no-rgb-first` 对比原深度入口。参考库从此前通过深度质量和前后 RGB 运动检查的成功会话构建，3D 点由 CAD 可见表面求交得到；缓存位于 `data/cache/rgb_pose_features/`。没有拷贝参考图位姿来代替当前帧 PnP，也没有放宽深度交接的运动拒绝规则。新增加的成功深度视角会在下次启动时进入参考库。

全部阶段继续使用同一个窗口。当前旧版 Astra 驱动无法同时保持 UVC RGB 和 OpenNI 深度流；真正采深度时仍短暂显示最后一帧，随后恢复实时 RGB。匹配参考充分的 RGB 路径已绕过切换；参考不足的视角仍会回到深度备用入口。任意新视角的运动识别仍需要更完整的多视角参考、RGB 6D 姿态模型，或可并发采流的驱动/SDK 与硬件方案。

本次修改前的代码副本位于 `data/tmp/before_camera_identity_and_motion/`；该副本已包含最早一部分按名称恢复相机的改动。
